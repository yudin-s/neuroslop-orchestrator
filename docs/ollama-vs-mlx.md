# Ollama (llama.cpp/Metal) vs MLX (mlx-lm) на Apple Silicon — что быстрее

Цель: зафиксировать выводы по производительности на одинаковом железе (Apple Silicon), чтобы не сравнивать вручную каждый раз.

## Короткий вывод

- Если важнее **скорость генерации** (token/sec на ответ, TG / throughput) и стабильная работа “из коробки”, чаще всего проще и быстрее стартовать с **Ollama (llama.cpp/Metal)** и подходящей квантизацией (Q4/Q5).
- Если важнее **длинные промпты и повторное использование одного и того же префикса** (много агентов с общей policy/контекстом), у **MLX/mlx-lm** есть сильная сторона в виде **prompt caching** и приёмов под длинный контекст.

Важно: результаты зависят от режима бенчмарка.
- **PP / prefill** (обработка промпта, часто bs>1)
- **TG / generation** (генерация новых токенов, обычно bs=1)

Сравнения часто “противоречат” друг другу, потому что меряют разные режимы и разные кванты.

## Что говорят источники (публичные данные)

### llama.cpp (Metal)
- Публичные бенчмарки Apple Silicon (таблицы PP vs TG, разные кванты).
- Пример на M1 Pro (16 GPU) для LLaMA 7B показывает TG (bs=1) порядка десятков tok/s в квантах (например Q4 заметно быстрее, чем FP16).
- Там же обсуждается, почему в PP (bs=512) FP16 может быть быстрее квантов: overhead dequant в compute-bound режиме.

Источник:
- https://github.com/ggml-org/llama.cpp/discussions/4167

### MLX / mlx-lm
- Официальный пример MLX демонстрирует бенчмаркинг и подчёркивает разделение стадий (обработка промпта vs генерация).

Источник:
- https://ml-explore.github.io/mlx/build/html/examples/llama-inference.html#weight-loading-and-benchmarking

- mlx-lm поддерживает подходы для длинных контекстов: rotating KV cache и prompt caching (полезно, когда множество запросов шарят длинный общий префикс).

Источник:
- https://github.com/ml-explore/mlx-lm/blob/main/README.md

- По speculative decoding в mlx-lm есть отчёты, где ускорение на быстрых 4-bit моделях небольшое из-за overhead проверки.

Источник:
- https://github.com/ml-explore/mlx-lm/discussions/890

### Ollama
- Ollama обычно рассматривают как удобную оболочку с API, которая использует бэкенды семейства llama.cpp/подобные.

Источник:
- https://github.com/ollama/ollama

## Рекомендация для M1 Pro 32GB (3B/7B/13B) под multi-agent

- 3B/7B: по умолчанию — **Ollama + Q4/Q5** (лучше latency/throughput и меньше “плясок” с окружением).
- 13B: чаще всего — тоже Ollama/llama.cpp с квантами и вниманием к контексту/памяти. Если бутылочное горлышко — длинные общие промпты (PP), рассмотреть MLX/mlx-lm ради prompt caching.

### Что важно для multi-agent
- Если агенты делают много коротких ответов: **TG** важнее → чаще выигрывает llama.cpp/Ollama.
- Если агенты постоянно “таскают” один огромный общий контекст: **PP** становится узким местом → MLX с prompt caching может дать выигрыш в этом конкретном режиме.

## Что мы делаем в этом репозитории

- По умолчанию используем Ollama (локально на хосте / Metal), а агенты могут быть изолированы в Docker.
- При желании можно добавить отдельный backend для MLX, но это отдельная интеграция (другой рантайм/сервер).
